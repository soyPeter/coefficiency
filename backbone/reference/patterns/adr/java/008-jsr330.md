# JSR-330 for Framework Independence

## Status

Accepted

## Context and Problem Statement

The application layer contains business logic orchestration that should not be tightly coupled to Spring Framework. We need a dependency injection approach that maintains Spring compatibility while allowing potential migration to other DI containers.

## Decision Drivers

* **Framework independence**: Application layer should not depend on Spring annotations
* **Portability**: Code should be usable with other DI containers (Guice, Dagger, CDI)
* **Standards compliance**: Prefer Java/Jakarta standards over proprietary annotations
* **Spring compatibility**: Must work seamlessly with Spring Boot

## Considered Options

* **JSR-330 (jakarta.inject)** - Standard dependency injection annotations (`@Named`, `@Inject`)
* **Spring Annotations** - Spring-specific (`@Service`, `@Component`, `@Autowired`)
* **Manual Wiring** - No DI annotations, manual bean configuration

## Decision Outcome

Chosen option: **JSR-330 annotations**, because they provide standard, portable dependency injection while remaining fully compatible with Spring's component scanning.

### Implementation

**Use Cases with JSR-330:**
```java
package io.bitnomio.customer.app;

import jakarta.inject.Named;

@Named  // Instead of @Service or @Component
public class CreateCustomerUseCase {

    private final CustomerCommandRepo customerRepo;
    private final EventPublisher eventPublisher;

    // Constructor injection (JSR-330 compatible)
    public CreateCustomerUseCase(
            CustomerCommandRepo customerRepo,
            EventPublisher eventPublisher) {
        this.customerRepo = customerRepo;
        this.eventPublisher = eventPublisher;
    }

    public Customer execute(CreateCustomerReq request) {
        // Business logic
    }
}
```

**Spring Configuration (unchanged):**
```java
@Configuration
@ComponentScan("io.bitnomio")  // Scans @Named as components
public class AppConfig {
    // Spring automatically discovers @Named classes
}
```

### Consequences

**Good:**
* Application layer is framework-agnostic
* Code portable to Guice, Dagger, CDI, or other JSR-330 implementations
* Follows Java/Jakarta standards
* No change to Spring configuration needed
* Constructor injection works identically
* Clear separation: `@Named` in app layer, Spring annotations only in infra layer

**Bad:**
* `@Named` less semantically clear than `@Service`
* Team must understand the distinction
* IDE may not provide Spring-specific features for `@Named` classes
* Requires `jakarta.inject` dependency

### Layer Annotation Guidelines

| Layer | Allowed Annotations | Examples |
|-------|---------------------|----------|
| Domain | None (POJO/Records) | Entities, Value Objects |
| Application | JSR-330 only | `@Named`, `@Inject` |
| Infrastructure | Spring annotations | `@Service`, `@Component`, `@Repository`, `@RestController` |
