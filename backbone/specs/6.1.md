# Spec 6.1: Move Jdbi injection from controllers into the service layer

Task: 6.1
PRD: backbone/1-PRD.md, "What good looks like", fourth bullet (the codebase follows the per-feature `domain/app/infra` layering)

## Context

Design rule 2 in `backbone/4-KNOWLEDGE.md` says services own data access and controllers never receive `Jdbi`; the NEVER DO list repeats it, and `backbone/guardrails.conf` blocks new `org.jdbi` imports in controller files. REVIEW.md finding W4 (and "Direct Jdbi usage in controllers") records the violation.

The task title names auth, billing and client. Those are already compliant: `AuthController`, `BillingController` and `ClientController` no longer reference `Jdbi` (their data access sits in `SqliteAuthRepository`, `BillingService` and `ClientService`). A grep of `services/coeff/src/main/java` on 2026-10-05 finds `Jdbi` in exactly four controllers, each through an injected constructor parameter stored in a field:

| Controller | Endpoints that use `Jdbi` directly | What the handler does with it |
|---|---|---|
| `simulator/ConceptsController` | `GET /api/concepts`, `POST /api/concepts`, `PUT /api/concepts/{id}`, `DELETE /api/concepts/{id}` | Raw SQL on `cost_concepts` (list ordered by name, insert, update, delete) |
| `simulator/SettingsController` | `GET /api/settings`, `PUT /api/settings`, `GET /api/fiscal`, `GET /api/fiscal/{key}`, `PUT /api/fiscal/{key}`, `GET /api/fiscal/working-days`, `PUT /api/fiscal/working-days` | Raw SQL on `settings` (list, upsert, `fiscal.*` lookup with JSON parsing) |
| `simulator/SimulatorController` | `GET /api/simulator/defaults`, `POST /api/simulator/calculate` | Reads `cost_concepts` with raw SQL and passes `Jdbi` to the static `SettingsHelper` for about 16 `fiscal.*` settings per request, with built-in fallbacks when a setting is missing |
| `consultant/infra/rest/ConsultantController` | `GET /api/consultants/{id}` | Raw SQL on `consultants`, mapped through `ConsultantRow`; other consultant endpoints already go through use cases and `ListConsultantsQuery` |

`simulator/FiscalController` declares the same five `/api/fiscal...` routes as `SettingsController` and delegates every one of them to `SettingsController`. It does not reference `Jdbi` itself.

Current behaviours that the refactor must keep (found by reading the code):
- `/api/simulator/defaults` and `/api/simulator/calculate` fall back to the working days `[20,19,23,19,21,22,21,22,22,20,21,19]` (sum 249) when `fiscal.workingDays` is missing. `GET /api/fiscal/working-days` returns `[]` in that case.
- `calculate` falls back to five built-in IRPF brackets when `fiscal.irpf_brackets` is missing, and reads every setting on each request (no caching).
- The concept endpoints don't validate input. A `type` outside `monthly`, `yearly`, `onetime` or a duplicate `name` is rejected by the database's CHECK and UNIQUE constraints and surfaces as a 500 error. `PUT` and `DELETE` on an unknown id succeed without changing anything.
- Errors are rendered as `{"error":"<message>","status":<code>}`. `NotFoundException` maps to 404 and `BadRequestException` to 400 (`ExceptionMapper`, `CoeffConfig`).

**Scope of this spec:** remove direct database access from these four controllers so that every controller in the service is compliant, with no change in observable HTTP behaviour. Auth, billing and client need no code change; this spec only checks that they stay compliant. Whether to retitle the task is an open question for the user; `3-TASKS.md` is not changed here.

## Requirements

- REQ-6.1-1: The system shall serve every HTTP endpoint without any REST controller holding, receiving or using a JDBI object (`Jdbi`, `Handle` or any other `org.jdbi` type); controllers shall obtain data only through the service layer. This covers all controllers, including auth, billing and client.
- REQ-6.1-2: The system shall keep the HTTP contract of the cost-concept endpoints (`GET`, `POST /api/concepts`, `PUT`, `DELETE /api/concepts/{id}`) unchanged: paths, methods, request fields, response fields, JSON types, ordering, status codes and stored effects.
- REQ-6.1-3: The system shall keep the HTTP contract of the settings and fiscal endpoints (`GET`, `PUT /api/settings`, `GET /api/fiscal`, `GET`, `PUT /api/fiscal/{key}`, `GET`, `PUT /api/fiscal/working-days`) unchanged, including the `fiscal.` key prefixing, the JSON parsing of `fiscal.*` values with fallback to the raw string, and the empty-list fallback for working days.
- REQ-6.1-4: The system shall keep the response of `GET /api/simulator/defaults` unchanged: the same six fields (`categories`, `schedules`, `coefDaysMonth`, `coefDaysYear`, `concepts`, `workingDays`) with the same values and the same fallbacks when settings are missing.
- REQ-6.1-5: The system shall keep the behaviour of `POST /api/simulator/calculate` unchanged: input validation with 400 before any calculation, the same result for the same input and stored settings, the same built-in defaults when settings are missing, and settings read on every request so that a stored change applies to the next request without a restart.
- REQ-6.1-6: The system shall keep the behaviour of `GET /api/consultants/{id}` unchanged: 200 with the consultant's representation when the id exists, and 404 with the message "Consultant not found" when it does not.

## Non-functional requirements

- Compatibility: no change to any route path, HTTP method, request field, response field name, JSON type, ordering or status code of the endpoints in REQ-6.1-2 to REQ-6.1-6. The frontend (`services/coeff/frontend`) needs no change.
- Data: no database schema change and no new Flyway migration. Data written before the change reads back identically after it.
- Build quality: `./gradlew build` passes with no new Checkstyle or SpotBugs findings (`7-CONVENTIONS.md`).
- Architecture hygiene: the change introduces no new finding in `harness.py scan`. In particular, no `org.jdbi`, `io.jooby` or `com.fasterxml.jackson` import is added under any `app/` or `domain/` package (`backbone/guardrails.conf`).
- Freshness: no caching of `settings` or `cost_concepts` is introduced. A write is visible to the next read request (AC-6.1-24).
- Performance: none beyond the above (single-user local application).

## Architecture
ADRs: ADR-002 (stack; package by feature with `domain/app/infra`; design rule 2 "services own data access"; features not yet layered migrate through the M6 tasks), ADR-003 (class-based JDBI repositories; its consequences name this task for `ConsultantController.getById()`), ADR-006 (simulator input validation stays at the controller boundary), ADR-007 (no schema change, so no migration).

No new ADR. Each choice below applies ADR-002 design rule 2 with a placement the codebase already uses: a feature-level service that holds `Jdbi` (as in `ClientService` and `BillingService`), and the consultant module's existing query port. These choices are interim. Tasks 6.2, 6.8 and 6.11 complete or replace them inside a single feature, with no consequence for other modules.

Tech requirements:

General rules
- Move the data access, don't rewrite it. Each `jdbi.withHandle`/`useHandle` statement leaves its controller with its SQL text, bind names, mapper (`mapToMap()`, `mapTo(String.class)`, `mapTo(ConsultantRow.class)`) and terminal call (`list()`, `findOne()`, `execute()`) unchanged.
- Leave all other controller code where it is, unchanged: route annotations, method signatures and return types, DTO records, the `"fiscal."` key prefixing, Jackson parsing and its fallbacks, the `io.jooby.value.Value` body handling, `validateInput`, the built-in fallback values, and the order of setting reads in `calculate`.
- Scope limits:
  - No new code under any `app/` or `domain/` package, no new subpackage in `simulator`, and no package moves (those are tasks 6.2 and 6.8).
  - No change to `CoefJdbiFactory`, `CoeffApplication`, `CoeffConfig`, `ExceptionMapper`, `SettingsHelper`, `FiscalController`, the auth, billing and client controllers, the Flyway migrations or the frontend.
  - The `mvc(...)` registration order in `CoeffApplication` stays as it is. `SettingsController_` is registered before `FiscalController_`, and both declare the `/api/fiscal...` routes.
- Errors: the new service methods have no try/catch and translate no exceptions. JDBI and parse exceptions propagate exactly as they do today. Wrapping them would change status codes:
  - `ExceptionMapper` maps `IllegalStateException` to 503.
  - `CoeffConfig` maps `IllegalArgumentException` to 400. This includes the `NumberFormatException` thrown for a malformed numeric setting.
  - Anything else becomes 500, including the CHECK and UNIQUE failures of AC-6.1-10.
  - This keeps REQ-6.1-2 to REQ-6.1-5 and the behaviours listed under Context.
- Transactions: none are added. Each service method runs its single statement in its own handle, as the controllers do today.
- Freshness (NFR): the new services are stateless `@Singleton`s whose only field is the injected `Jdbi`. There is no caching, memoisation or pre-loading. `defaults` and `calculate` read every setting on each request, in the current order (AC-6.1-24).
- Wiring:
  - The new services are Avaje `@Singleton`s with an `@Inject` constructor that takes the shared `Jdbi` bean from `CoefJdbiFactory`, as `ClientService` does. Never call `SqliteConnection.jdbi()` directly.
  - No `@Named` qualifiers and no new factory beans.
- Controller files (any file with a Jooby `@Path` or named `*Controller.java`) must not contain the text `Jdbi`, `Handle` or `org.jdbi` anywhere, including Javadoc and comments, because AC-6.1-1's regex matches text.
- Architecture hygiene (NFR): the new files are services in the flat feature package. They match none of the `app/`, `domain/` or controller rules in `backbone/guardrails.conf`, so `harness.py scan` gets no new finding.
- Language level: Java 21. The java skill's examples target Java 25, so use only features that are final in Java 21 (no unnamed `_` variables, no stream gatherers).

Simulator: the flat package `io.bitnomio.coeff.simulator`, which task 6.8 will layer
- New `CostConceptService` in the same package:
  - `List<Map<String, Object>> list()`: `SELECT * FROM cost_concepts ORDER BY name` with `mapToMap()`.
  - `void create(String name, String type, double defaultValue)`, `void update(int id, String name, String type, double defaultValue)` and `void delete(int id)`, each with the current statement.
  - The methods take plain values, not `ConceptsController.ConceptReq`, so the service doesn't depend on the REST DTO.
  - Rows stay `Map`s, with no typed row record, so the JSON keys, value types and order don't change. Typed rows belong to task 6.8.
- `ConceptsController`:
  - Its constructor takes `CostConceptService` instead of `Jdbi`.
  - Each handler makes exactly one service call. `ConceptReq` stays in the controller.
- New `SettingsService` in the same package:
  - `List<Map<String, Object>> findAll()`: `SELECT key, value FROM settings ORDER BY key`.
  - `List<Map<String, Object>> findAllFiscal()`: `SELECT key, value FROM settings WHERE key LIKE 'fiscal.%'`, with the literal unchanged.
  - `Optional<String> find(String key)`, `int readIntOrDefault(String key, int defaultValue)` and `double readDoubleOrDefault(String key, double defaultValue)`. These three delegate to `SettingsHelper.getSetting`, `readIntOrDefault` and `readDoubleOrDefault` with the injected `Jdbi`. That keeps the single-key SQL and the `Integer.parseInt`/`Double.parseDouble` behaviour in one place.
  - `void upsert(String key, String value)`: the current `INSERT ... ON CONFLICT(key) DO UPDATE` statement, which the three upsert handlers share.
- `SettingsController`:
  - Its constructor takes `SettingsService` instead of `Jdbi`.
  - `getFiscal` returns `find("fiscal." + key).orElse(null)`.
  - `workingDays` uses `find("fiscal.workingDays").orElse("[]")`, followed by the existing parse and its `List.of()` fallback.
  - `allFiscal` keeps its loop and its `ObjectMapper` parsing, now over `findAllFiscal()`.
  - `upsert`, `upsertFiscal` and `upsertWorkingDays` call `upsert(...)` with the same keys and values as today.
  - The per-call `new ObjectMapper()` stays (REVIEW.md W6, out of scope).
- `FiscalController` is not changed. It keeps delegating to `SettingsController`, has no `Jdbi`, and so already meets REQ-6.1-1.
  - `SettingsController` and `FiscalController` declare the same routes. Whichever declaration Jooby resolves, behaviour stays identical only while both run the same code.
  - Routing `FiscalController` to the service belongs to the duplicate-route cleanup (Q4, task 6.8).
- `SimulatorController`:
  - Its constructor is `(SimulatorService, CostConceptService, SettingsService)`.
  - `defaults` gets the concepts from `CostConceptService.list()`.
  - Each `SettingsHelper.getSetting(jdbi, k)`, `readIntOrDefault(jdbi, k, d)` and `readDoubleOrDefault(jdbi, k, d)` call becomes the matching `SettingsService` method, with the same key and default, in the same order.
  - The `SettingsHelper` import goes. `validateInput`, `MAPPER`, `loadBrackets`, `loadSsCategories`, `loadWorkingDays` and the built-in fallbacks stay in the controller, unchanged. Moving the fiscal-config assembly into the service layer belongs to task 6.8.
- `SettingsHelper` (`shared/util`) is not changed. `BillingService`, `ReportService` and `BonusBreakdownCacheService` still call it (tasks 6.6 and 6.11).
  - After this task, the simulator reaches it only through `SettingsService`.
  - Whether a shared settings port replaces it is decided in task 6.11.

Consultant: already layered
- `ListConsultantsQuery` (`consultant/infra/data/sql`) is the module's query port, which `GET /api/consultants` already uses. It gains `Optional<ConsultantRow> findById(long id)`.
  - `SqliteConsultantQueryRepo` implements it with the controller's current statement, verbatim: `SELECT * FROM consultants WHERE id = :id` with `bind("id", id)` and `mapTo(ConsultantRow.class).findOne()`.
  - The mapping uses the `ConsultantRow` mapper that is registered on the shared `Jdbi` (ADR-003).
- `ConsultantController`:
  - Remove the `Jdbi` constructor parameter, field and import.
  - `getById` returns `listQuery.findById(id).map(r -> ConsultantRes.from(r.toDomain())).orElseThrow(() -> new NotFoundException("Consultant not found"))`.
  - The message stays "Consultant not found" (AC-6.1-26). The use cases use a different message, "Consultant not found: <id>".
- Do not use `ConsultantAction.findById` (the command port bound as `@Named("consultantCommand")`), and do not add a `GetConsultantUseCase`. That would route a read through the write side, and nothing shows that its SQL and filters match the current query (the design notes describe soft delete), so AC-6.1-25 could change.
- Precondition: the `consultant/infra/data/` package is missing from the repository (Q6).

Tests (the recommended default of Q5)
- Characterization tests come first:
  - Write the endpoint tests against the pre-change code and commit them while they pass.
  - Then refactor in a separate commit that doesn't modify those tests.
  - Where an AC says "same as the pre-change build", the expected value is a literal captured from that first run. Examples: the `calculate` result fields, the status, Content-Type and body of `GET /api/fiscal/unknown_key`, and the statuses of `POST`, `PUT` and `DELETE /api/concepts`.
- Endpoint tests:
  - Location: `services/coeff/src/intTest/java/io/bitnomio/coeff/...`, in `*IT.java` classes such as `simulator/ConceptsControllerIT`, `simulator/SettingsControllerIT`, `simulator/SimulatorControllerIT` and `consultant/infra/rest/ConsultantControllerIT`.
  - Each test class starts the real `CoeffApplication` on a free loopback port. That gives the production routes and registration order, the auth filter and both error handlers.
  - Set the system property `coeff.data.dir` to a JUnit `@TempDir` before the application is constructed. Set `java.awt.headless=true` so that the start hook opens no browser.
  - Get a token through the `/api/auth/*` flow and call the endpoints with `java.net.http.HttpClient`.
- Test data: tests reset and seed `settings`, `cost_concepts` and `consultants` through a test-only `Jdbi` on `<tempdir>/coeff.db`. The first start seeds default settings and concepts, so each test clears these tables first.
- No new dependency and no Testcontainers. SQLite is embedded, and ADR-002's Testcontainers covers external services, of which there are none here.
- `services/coeff/build.gradle.kts`: the existing `intTest` task needs `useJUnitPlatform()` (without it Gradle runs no JUnit 5 tests) and `systemProperty("java.awt.headless", "true")`. No other build change. Run the tests with `./gradlew :services:coeff:intTest` (see Q7).
- Static checks for AC-6.1-1, AC-6.1-3 and the controller rule of AC-6.1-2:
  - A unit test, `services/coeff/src/test/java/io/bitnomio/coeff/ControllerJdbiFreeTest.java`, finds the controller files under `src/main/java` as AC-6.1-1 defines them. It asserts that none matches `org\.jdbi|\bJdbi\b|\bHandle\b`, and names `AuthController`, `BillingController` and `ClientController` explicitly.
  - The full `harness.py scan` comparison (AC-6.1-2) and the no-diff check on those three controllers (AC-6.1-3) are run by the implementer and by the judge.
- Test rules:
  - Use JUnit 5 and AssertJ, and put the AC id in `@DisplayName`.
  - Write nothing outside the temp dir.
  - Never log consultant fixture data.
