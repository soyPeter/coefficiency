# Security: Authentication, Token Validation & Database Encryption

## Summary

Three security layers: password-based auth with HMAC-signed session tokens and backend validation, AES-256-GCM database encryption at rest, and auto-logout idle timer.

## Grilling

### Scope
- **Q:** What security features exist?
- **A:** User setup (create first account), login with SHA-256(salt+password) verification, HMAC-SHA256 signed tokens, before-filter on all /api/* routes (except exempted) validating Bearer token, 401 response on invalid/missing token, 503 on missing DB, frontend auto-redirect to login on 401/503. DB file AES-256-GCM encrypted on disk, decrypted to temp file during session, re-encrypted on logout/shutdown.
- **Q:** What is out of scope?
- **A:** OAuth, SSO, multi-factor auth, role-based access, audit logging, HTTPS/TLS.

### Boundaries
- **Q:** What modules are touched?
- **A:** auth/ (AuthService, DbEncryption, AuthController, AuthRepository, SqliteAuthRepository), shared/ (SqliteConnection, ExceptionMapper), App.java (before-filters, shutdown hook). Frontend: api.ts (request wrapper with auth headers), App.tsx (auth:unauthorized handler).
- **Q:** What must NOT change?
- **A:** Existing API contracts. The HMAC secret constant approach (acceptable for local desktop). Password minimum lengths (3 for username, 4 for password).

### Data & State
- **Q:** What new data structures?
- **A:** DbEncryption manages AES key derived from password via PBKDF2. .db-key file stores salt + SHA-256 verifier. app.db.enc is encrypted DB. .app.db is decrypted temp.
- **Q:** Where does state live?
- **A:** Token in localStorage. DB connection only while authenticated. .app.db only while running. .db-key and app.db.enc always on disk.

### API
- **Q:** What endpoints are exempt from auth?
- **A:** GET /api/auth/status, POST /api/auth/setup, POST /api/auth/login, POST /api/auth/logout, GET /api/health, /openapi*, /swagger*, /redoc*.
- **Q:** What are the error responses?
- **A:** 401 → {"error":"Unauthorized"} (invalid/missing token). 503 → {"error":"DB not connected"} (DB not yet decrypted).

### Implementation Order
- **Q:** First security feature?
- **A:** Login + HMAC tokens + before-filter (M20). Then DB encryption (M21). Then auto-logout (M19).
- **Q:** Dependencies?
- **A:** Auth filter depends on AuthService.validateToken(). DB encryption depends on SqliteConnection lazy init. Auto-logout independent.

## Requirements

### REQ-SEC-001: User Setup
WHEN no user exists, the system SHALL allow creating the first account with username (3+ chars) and password (4+ chars).

### REQ-SEC-002: Login
WHEN the user provides valid credentials, the system SHALL return an HMAC-SHA256 signed token.

### REQ-SEC-003: Token Validation Middleware
WHEN a request arrives at a non-exempt endpoint without a valid Bearer token, the system SHALL return HTTP 401.

### REQ-SEC-004: Frontend Token Delivery
WHEN the frontend makes an API request, the system SHALL include the Bearer token in the Authorization header.

### REQ-SEC-005: 401/503 Auto-Logout
WHEN the frontend receives 401 or 503, the system SHALL clear the token and redirect to the login page.

### REQ-SEC-006: DB Encryption at Rest
WHEN the application is not running, the SQLite file SHALL be AES-256-GCM encrypted on disk.

### REQ-SEC-007: Password-Derived Key
WHEN encrypting the database, the system SHALL derive the key via PBKDF2-HMAC-SHA256 (100k iterations).

### REQ-SEC-008: DB Decryption on Login
WHEN the user logs in successfully, the system SHALL decrypt the database before opening the SQLite connection.

### REQ-SEC-009: DB Re-Encryption on Logout
WHEN the user logs out, the system SHALL re-encrypt the database and delete the decrypted temp file.

### REQ-SEC-010: Periodic DB Sync
WHILE the database is connected, the system SHALL re-encrypt the temp file every 5 minutes to limit crash data loss.

### REQ-SEC-011: sendBeacon Logout
WHEN auto-logout triggers, the system SHALL use navigator.sendBeacon to notify the backend before page unload.

### REQ-SEC-012: Password Hashing
WHEN storing the user password, the system SHALL use SHA-256 with a per-user 16-byte random salt.
